## A. Verdict

**Shore-up-first — narrowly, and only for the planned expansions.** The single strongest reason: `moa/client.go` has **zero transport-level recovery** — no retry, no backoff, no 429/rate-limit awareness, no `Retry-After` handling — while all three comparators (codex, grok, dsh) treat transient failures as a first-class, bounded, policy-driven class. That absence is inert for today's one-shot review/panel/vision traffic, but the planned load (distill/curator/learner onto `Query`; a consolidator on one `Query`; design legs fanning 16-round `QueryWithTools` chains scoped to a repo root) multiplies both request count and per-request blast radius. Today a single transient 429 or gateway 5xx aborts an entire multi-model review fan-out or a 15-minute design leg with no automatic recovery and no 429 signal for the caller to back off on. Everything else — truncation policy, thinking-block replay, tool round-cap semantics, test posture — is already at or above peer quality.

## B. moa/client.go quality assessment

### Strengths (evidence-cited)

1. **Wire exactness for Anthropic Messages is genuinely hard-won.** `client.go:messageResponse` keeps `rawContent` via a second unmarshal pass (`client.go:post`), so the tool loop echoes the assistant turn byte-verbatim instead of re-marshaling the cooked struct that drops unknown thinking fields ("thinking"/"signature"). The comment documents the observed kimi-k3 400 (`thinking.thinking: Field required`), and `client_test.go:TestQueryWithToolsReplaysAssistantVerbatim` pins the echo round-trip `reflect.DeepEqual`. This is the exact class of provider quirk the comparators do *not* need to absorb (they own the wire or translate).
2. **stop_reason handling is fail-loud, not silent.** `client.go:classifyStop` whitelists known reasons, treats `pause_turn`/unknown as `end_turn` **but logs both**, and errors `refusal`/`model_context_window_exceeded` as terminal. The comment explicitly rejects silent fallthrough. Peers handle this too (codex `ApiError::ContextWindowExceeded`, `CyberPolicy`; grok `provider_error.rs`), but moa's is defense-in-depth against gateway drift — the documented 2026-08-09 sweep.
3. **Output-budget policy is a falsifiable ledger, not a silent retry.** `client.go:outputBudget.escalate` doubles `max_tokens` on truncation (≤3 bumps, per-model hard cap from `internal/modelspec/modelspec.go`), records every bump in `Result.Escalations`, and the truncation strategy *splits by content*: truncated display answers ship flagged (`Result.Truncated`) while a truncated `tool_use` is **never executed** — the whole turn is re-issued at the doubled budget (`client.go:QueryWithTools`). grok *explicitly never retries `MaxTokensTruncation`*, so odo's reissue is ahead of at least one peer.
4. **Timeout math derives from the payload, with a documented floor.** `client.go:requestTimeout` = 900s base + `max_tokens/120` headroom; the floor covers long server-side thinking on max-effort legs. Tests pin both the floor bound and the 65536-token math (`TestRequestTimeoutFloor`, `TestRequestTimeout`).
5. **Test posture is strong and contract-pinned.** `client_test.go` (~431 lines vs ~627 impl) uses `httptest` servers to pin: headers/auth, URL path, default-model wiring, per-model initial budgets (`TestQueryPerModelInitialBudget`), the escalation ledger (`TestQueryEscalatesOnMaxTokens`), hard-cap partial vs empty-partial split, stop-reason classes, verbatim replay, truncation-reissue-without-consuming-a-round, and the default 16-round cap being the ceiling.
6. **Credentials hygiene is right-sized.** Key comes from an env-var name (`SUDO_CODING_KEY`/prefs-configured) only; empty key fails early and the error names the env var; callers scrub the base URL before journaling (`server.go:reviewWithModel` → `scrubBaseURL`). Non-200 bodies are trimmed to 512 bytes (`errBodyTail`) so gateway diagnostics surface instead of a generic "check server logs".

### Weaknesses

1. **No retry/backoff/429 layer.** `client.go:post` returns an error on any non-200 with no retry classification, no `Retry-After` read, no transient-vs-terminal distinction, and no connection-error retry. Every comparator has all of this (see matrix).
2. **Errors are `fmt.Errorf` strings; callers can't classify.** `server.go:reviewWithModel` must treat *every* moa error as `Infra:true` because there is no typed error to distinguish 401 (config) from 429 (throttle) from timeout. Fine today; not once a consolidator wants to degrade one leg without killing the chain.
3. **Each attempt gets a fresh full `requestTimeout`, and the only non-truncation "retry" is a whole-turn re-issue at a doubled budget.** A hung gateway can hold a caller for 900s+ of silence with no liveness; 16 tool rounds × up to ~24 min worst-case each ≈ hours of daemon goroutine occupancy with zero cancellation except caller `ctx`. Acceptable for one-shots; a latency risk for design legs.
4. **16 is both the default and the ceiling for tool rounds** (`defaultToolRounds` == `maxToolRounds` == 16, documented as a recent emergency raise from 8). No caller-visible way to raise it for deeper chains.
5. **`apiVersion` hardcoded `2023-06-01`; single hardcoded gateway default; no per-model wire negotiation.** Works for the current catalog; brittle if an expansion needs a newer protocol feature.
6. **No request/response logging beyond the daemon journal.** Debugging an actual wire skew requires curl.

## D. Gaps worth fixing (ranked)

1. **Transport retry / 429 awareness** — *Evidence:* `client.go:post()` fails immediately on any non-200; every comparator has a bounded policy (codex `RateLimit/Retryable/ServerOverloaded`; grok `retry.rs` 14-try budget, `Retry-After` + `x-should-retry` + 429 threshold; dsh `RATE_LIMIT` + `retry-after`). *Fix:* bounded re-post loop for 429/5xx/connection-error, honor `Retry-After` (clamp), **never retry** 400/401/403/408/422/525/526 (a bad key must stay fail-loud), surface retryable/rate-limited class. *Cost:* **M**. *Wave:* W1-W2 (before any expansion relies on this wire). *Priority:* **P1**. *Confidence:* High (— documented in all peers).
2. **Typed error classes** — *Evidence:* `server.go:reviewWithModel` forces `Infra:true` because moa returns fmt strings. *Fix:* `type Error { Status int; Class Transient|RateLimit|Auth|Terminal|InvalidRequest; Msg }` threaded from `post`/`oneShot`. *Cost:* **S*. *Wave:* W1. *Priority:* **P1**. *Confidence:* High.
3. **Loop-wide progress/cancellation plan for long chains** — *Evidence:* one 65536-token attempt = ~24min; 16 rounds → up to hours with zero liveness and only caller `ctx` as cancel. *Fix:* caller-level `context.WithTimeout` per design leg; optionally per-round byte-progress; keep per-attempt timeout free-standing. *Cost:* **S**. *Wave:* W3 (design legs). *Priority:* **P1**. *Confidence:* High.
4. **Image re-encode on escalation** — `client.go:QueryWithImages` base64-encodes same images inside `mkBody` per attempt; truncation re-encodes up to 3×460s. *Fix:* encode once before `oneShot`. *Cost:* **S**. *Wave:* W1. *Priority:* **P2**. *Confidence:* High.
5. **No context-window accounting across tool rounds** — *Evidence* transcript grows per round; a design leg approaching the model's context window ends in `stopTerminal` (`model_context_window_exceeded`) — whole leg lost, no partial, no compaction hook.*Fix:* approx. token accounting per round in `QueryWithTools`; when >~70% of `modelspec.ContextWindow`, force a "summarize-and-answer" prune or fail fast with a clear signal.*Cost:* **M*. *Wave:* W3. *Priority:* **P2**. *Confidence:* Medium.
6. **Hardcoded `apiVersion` + single default endpoint** — no per-model wire negotiation a future protocol feature needs. *Fix:* hoist version into `Client`. *Cost:* **S**. *Wave:* W4. *Priority:* **P2**. *Confidence:* Medium.

## E. What the peers do that moa must NOT copy

1. **Codex's session/turn client stack** — `ModelClientSession`, cached Websocket, sticky `x-codex-turn-state`, incremental append, precondition prewarm. moa is deliberately session-less one-shot; copying turns the truncation problem (already solved well) into a reconnection/state problem.
2. **Codex governance surface** — attestation, cyber policy, subagent credential handoff. Security in odo belongs to the daemon (the scoped executor), not a leaf API client; ballooning a 630-line core is the anti-goal.
3. **Grok's 3-wire multiplexer / doom-loop resampling / 413-image-strip retry** — moa is one wire through a translating gateway; retry-by-resample or by-request-rewrite hides who said what and is a *different* product's design. Notably their `Never retry max_tokens` is a deliberate product stance opposite to moa's escalation, and moa's is right for `max_output`.
4. **dsh's full consumer-facing BYOK config surface** (remembered provider catalog, `discoverModels`, per-provider settings namespaces). Host RPC topology is a separate product branch, not a client concern.
5. **The leaky-jiter observability surface** (case Names). moa journals enough for its one user (the daemon); a full metric stack is overhead for a one-shot.

## F. Risks the planned expansions put on this client + mitigations

- **Distill/learner/curator to `Query`** — these are single-shot but longer-context (full conversation distill). *Risk:* they may want larger `contextWindow`/output than `modelspec` fallback (unknown models get 16384 initial / 32768 cap) — current migration passes the fallback budget and can silently truncate on a model not in the table. *Mitigation:* ensure the estimated distill models get explicit `modelspec` entries (which the table already extends to) — a quick additive map, not a client change.
- **Design-MoA consolidator (single `Query` synthesizing 3 proposals)** — *Risk:* one request must synthesize a large 3-print corpus; input could approach the context limits; a truncated consolidator (stop `max_tokens`) re-issues the *whole* corpus at 2× — effectively 2× payload each escalation. That's correct but expensive. *Mitigation:* keep the per-model budget table conservative on these models; surface `Result.Escalations` so the caller can pre-compact the three proposals if escalation count exceeds 1.
- **Design legs on `QueryWithTools` scoped to a repo root** — *Risk A*: resize context — a 16-round loop with repo-root reads (64KB `read_file`) can exhaust a 200K-window model before the answer; terminal `model_context_window_exceeded` = the leg fails wholesale with no partial. *Mitigation:* use the 3-tool executor's existing caps (64KB/2000 lines/500 matches) *plus* add round-trip token accounting (gap 5) or cap tool result size for design-legs. *Risk B*: 16-round cap = ceiling cannot be raised for complex design chains. *Mitigation:* allow the caller to raise the cap explicitly (keep 16 as default), paired with the loop-deadline (gap 3). *Risk C*: scope is enforced only by `fscastools`' `check/resolve` under the executor's root — a design leg scoped to the repo root is a *new* executor instance rooted there; if the caller defaults to `newFSToolExecutor()` (home-rooted), legs silently read outside the repo root the same secrets a /panel would (the deny-list then is the only bulwark). *Mitigation:* pass an explicit repo-root root to the executor before any leg runs (caller-side; not a client gap).
