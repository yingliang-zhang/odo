## A. Executive summary

Three harnesses, three interaction postures. **dsh** (web-only React, no TUI) is a durable-log session host: every UI panel folds state from server-side projections, and a headless mode with `never`-approval is the CI posture — the browser is one of several clients on one host. **grok** (ratatui fullscreen) is a multi-session orchestrator: per-agent task/queue panes, a dashboard with `NeedsInput` rows you answer via peek-without-popup, word-scoped persistent permission grants, and an inline plan-approval surface with comment-and-feedback. **codex** (ratatui + app-server) is a focused single-thread TUI whose standout is the approval ledger: transcript cells for every review decision (including Guardian auto-review and timeouts) and a sophisticated model/effort config system. For Odo's long-autonomy vision the consequential gaps are: (1) queue-and-interject steering (grok is best; all three have it differently), (2) review surfaces that degrade gracefully instead of blocking (codex auto-review + grok peek, vs codex's legacy full-screen patch gate), and (3) scoped remembered grants (grok's word-scope allow/deny and `Allow all edits this session` — direct fuel for Odo's gating ladder). Odo already wins on always-visible multi-panel webview monitoring (LedgerPanel/MemoryPanel/StatusBar/ToolTicker) and mouse-friendly Accept/Reject lanes.

## B. Frontend-architecture table + key divergences

| | dsh (deepseek-harness) | grok (grok-build) | codex (openai/codex) |
|---|---|---|---|
| UI shell | React 18 + CSS Modules, Cordis plugin slot tree inside browser | Rust ratatui; custom `xai-ratatui-textarea`, `xai-ratatui-inline`, `xai-grok-markdown`, `xai-grok-pager` | Rust ratatui + custom keymap/chords, streaming controller, transcript cells |
| Agent linkage | RPC over HTTP POST + WS streams → one host serves all tabs | ACP ext-notifications consumed by a per-agent actor; shared queue + dashboard | app-server RPC; threads, sidebar, replay |
| Session authority | `ctx.sessions` in the host; browser is a view | pager + daemon; dashboard is multi-session | app-server threads; TUI detects one primary thread |
| Rendering | projections (`useProjection`) + durable log replay | per-pane state; scrollback reducer folding `session/update` | history cells / transcript cells; `markdown_stream` |
| Multi-client | yes (tabs, multi-tab sync) | no; one fullscreen | no; IDE/desktop extras |

Key divergences: (1) dsh is the only web multi-client shell; grok and codex are terminal-dominant. (2) grok is session-grid-first (dashboard), codex thread-first, dsh chat-first per tab. (3) dsh keeps the UI spec thin by pushing `session/projection` server-side; grok/codex fold streams in the client — dsh's model is the cleanest for the "monitor long autonomy from anywhere" case.

## E. Anti-patterns (what Odo should NOT copy) + already-better

**Anti-patterns:**
- **Blocking modal review of diffs (no park path).** codex treats the patch gate as a full-screen event (`enter_alt_screen` + `DiffSummary` overlay) and even logs "Legacy patch approval requests are not available in TUI yet" — a stale or inaccessible|modal path is a dead turn under long autonomy. Resolve: the diff review should *appear* only when the gating ladder demotes; otherwise never surface.
- **Single-key turn-cancel (Esc) as a general default.** grok's adaptive `escWouldCancelTurn` is carefully staged, but bare-Esc-cancels is spray-painted through many panes; with a long unattended session one stray Esc kills a working agent and misses review-pointer energy. Odo should use an explicit **Stop** action (and confirm guest turns not accidentally kill).
- **Typing-number approval inside a scrolling (numbers 1-9)** in dashboard peek: ambiguous with keys typed for search; abrupt `. Add: **"tell me what to do differently" via inline prompt** — good, but don't make the text field the only way to defer: a "defer/park" button is more desktop-sane.
- **Per-session-scope "Always allow" near* **word*wave locating with arrows** (grok ←/→) is TUI optimization; in a desktop GUI, expose scope as clicked chips.

**Odo (per shipped component list) already does better than all three:**
1. **Always-visible multi-panel monitoring** — LedgerPanel (timeline of approvals/apps), ContextPanel, MemoryPanel, ToolTicker, StatusBar, Sidebar, TopBar in one web surface. grok and codex TUIs report one full-screen at a time; continuous autotext, decisions, and memory demand.
2. **Mouse-first Accept/Reject lanes** — DiffViewer renders diff lanes with clickable Accept/Reject; TUIs use keyboard-only commands; desktop GUI = the right affordance.
3. **CommandPalette + PlanChip sidebar** — grok's approach is slash-command only; codex uses `@`-mentions and pickers. Odo separates "command as typed" (palette) from "plan as committed" (chips) cleanly.

## F. Surprises / unexpected finds

- **grok is effectively a multi-session orchestrator turn watcher CLI** — dashboard with 4-row state colors, background tasks pane and scheduled/cron prompts; not merely a single-agent TUI.
- **codex auto-review is exposed as an explicit approval ledger**, not just internal: cells for "request denied", "review timed out", with `approveGuardianDeniedAction` ironically making the TUI as UI-first as Odo's gating-ladder on the auto-session side.
- **grok permission UX is deep**: word-scoped allow/deny with `always_allow_scope_persists` refusing scopes for dangerous commands, argv-ambiguous cases, and MCP server-vs-tool scope labels — the route to actually "remember, but minimize blast radius".
- **dsh's entire web UI derives from server-side projections (`session/projection`)**, making multi-tab sync trivial — architecture Odo's desktop GUI could reuse for cross-View states long autonomy.
- **grok has a `/rewind` + `/jump` pair** — one mutating (rewind) and one read-only viewport jump (Esc restores) — a considered undo pattern worth copying split-genome.
