# Tri-Model## A. Executive summary

Report persisted at `/tmp/harness-gui-runs/out-k3.md` (47 KB, 191 table rows, 6 sections). Full deliverable follows.

Three harnesses encode three distinct interaction philosophies. **dsh** is a React-18/Vite SPA (~30 browser-side Cordis plugins) talking HTTP-POST uplink + two downlink-only WebSockets to an in-process core; its approvals are deliberately one-shot-only, diffs display-only, and "multi-session" is a sidebar list over a single-occupant stage. **grok** is one Rust binary whose ratatui TUI embeds the agent core on a thread over typed Zed-ACP + `x.ai/*` channels; it ships the most interaction-complete surface audited — dashboard cockpit, plan review with per-line comments, hunk accept/reject that rewrites disk, checkpoint rewind — all keyboard/mouse, zero i18n. **codex** inverts the picture: the TUI contains no core at all; it embeds *its own app-server* in-process and speaks v2 JSON-RPC (`InProcessAppServerClient`), so TUI, VS Code, desktop, and headless `exec` are peers on one thread/turn authority. For Odo, the strongest borrowables are dsh's context-pressure meter + durable steering queue, grok's attention-ordered cockpit + background-work status line + per-scope review actions, and codex's fork-before-turn backtrack. The decisive divergences: approval philosophy (one-shot vs session-scoped vs rule-editing), concurrency UX (sidebar vs dashboard vs attachable daemon), and change-review timing (display-only vs post-hoc disk surgery vs pre-execution preview) — all three directly feed Odo's gating-ladder + parked-review design.

Repo abbreviations: **dsh** = `deepseek-ai/deepseek-harness`, **grok** = `xai-org/grok-build`, **codex** = `openai/codex`. Paths relative to each repo root (clones at `/tmp/harness-src-k3/{dsh,grok,codex}`).

**Three most consequential interaction divergences:**

1. **Approval philosophy / trust ladder.** dsh caps the vocabulary at allow-once (`packages/interaction/user-approval/README.md`): every risky action is a modal composer takeover, forever. codex offers per-scope session memory ("don't ask again for this command / these files / this host", `approval_overlay.rs:871-878,1024`). grok goes furthest — the prompt itself edits durable machine-readable rules (word-scope ←/→, `PatternEdit` glob, MCP scope), plus six modes and admin lockout. Three points on a "friction vs remembered trust" spectrum: none, recall, authored policy.
2. **Concurrency UX.** grok is dashboard-first: several live agents in one process, state-ordered, peek-reply, dispatch (`docs/user-guide/23-dashboard.md`, `app/roster.rs`). dsh multiplexes data (mux stream) but presents a single-stage sidebar (`pendingInteraction` dots). codex multiplexes authority (one app-server, many threads) and lets any client attach; its TUI surfaces cross-thread state only as an approval inbox (`PendingThreadApprovals`). Center of gravity: worklist (grok) vs conversation (dsh) vs authority (codex).
3. **Change-review timing.** dsh reviews *before* execution (its only gate) and displays applied diffs read-only. codex reviews *before*, richly (full-screen diff approval with scope options) and rewinds after (`thread/rollback`). grok reviews *after*: hunks are applied, then accept/reject patches the working tree back (`xai-hunk-tracker::reject_hunk`). This is the direct analogue of Odo's parked-review bet — and grok is the only peer validating that post-hoc review works.
