## A. Executive summary (≤10 lines)

Three coding-agent harnesses, three radically different frontend philosophies. **dsh** is a web-only React/Vite app with HTTP-up/WebSocket-down transport and the most extensible slot-based plugin composition. **grok** is a fullscreen ratatui TUI backed by a decoupled UDS leader daemon, with the richest background-work visibility and most granular permission-scope UX. **codex** is a ratatui TUI over a JSON-RPC app-server daemon (in-process or remote), with the most durable state model (SQLite-backed queue, backtrack/fork-rewind) and the most configurable status surface. All three share one flaw for Odo's use case: approvals are **synchronous blocking prompts** with no "park for async later" concept — none implements Odo's vision of parked reviews replacing sync gates. None has per-file Accept/Reject diff lanes (dsh/grok diffs are presentation-only; codex diffs are inline scrollback + bottom-pane modal). The most consequential divergences are (1) transport architecture (HTTP/WS vs UDS-leader vs JSON-RPC app-server), (2) background-work model (read-only jobs vs unified tasks pane with /loop/monitor vs background terminals + subagent dots), and (3) state durability (host-projection vs on-disk JSONL vs SQLite). Odo's existing DiffViewer lanes, MoA review_diff gating ladder, and multi-workstream model are already ahead of all three on the autonomy axis.

(3) Surface breadth: codex has the widest surface spread (TUI+exec+cloud-tasks+IDE+desktop) all sharing one protocol — a template for Odo's "one daemon, many surfaces" goal.

**3 most consequential interaction divergences:**

1. **Background-work model** — grok's unified tasks pane (Ctrl+G) with live line-count badges, `/loop` recurring tasks, `monitor` event streams, and a persistent still-running cue above the prompt is a categorically richer visibility model than dsh's read-only job popover (no completion notification, no cancel) or codex's scattered `/ps` + subagent dots + separate cloud-tasks app. This is the single biggest UX gap for Odo's "long unattended autonomy with concurrent runs."

2. **Approval granularity and durability** — grok's permission scope-widening (←/→ word-by-word, `e` glob-edit, Tool-vs-Server MCP scope, remembered per-project grants with 5-step precedence) is the most graduated; codex's `AcceptForSession` is the only session-scoped trust bump; dsh is allow-once-only. All three block synchronously. None has a "park this approval for async later" concept — the exact feature Odo wants.

3. **Session-state durability** — codex's SQLite-backed `SqliteQueueStore` (durable thread-scoped queued input surviving restarts) + `BacktrackState` (source-preserving fork-rewind) is the strongest durability model; grok's per-session JSONL directory is comprehensive but less queryable; dsh's host-projection model is conceptually clean but the client holds only thin ephemeral overlays. For Odo's "long autonomy" this determines whether a queued steering message or pending review survives a daemon restart.

## E. Anti-patterns to avoid + what Odo already does better

### Anti-patterns Odo should explicitly NOT copy

1. **Synchronous blocking approvals with no "park for async later"** — All three repos block the agent on a modal approval prompt. dsh: `ApprovalPanel` "one-shot refuse/allow only" (`ui-conversation/README.md`). codex: `tool_requests.rs:on_guardian_assessment` owns the live status footer until resolved; `effective_available_decisions` is a finite per-action enum with only `AcceptForSession` as remember-scope. grok: `PermissionViewState` blocks the prompt area. **None** has a "park this review" concept. This directly fights Odo's vision of "async parked reviews replace sync gates." Odo should keep its daemon-owned `reviewDiff` (MoA) model and add a parked-review queue, not copy any of these blocking modals.

2. **Presentation-only diffs with no Accept/Reject gating lane** — dsh `DiffBlock` (`ui-primitives/README.md`) and grok `EditToolCallBlock` (`scrollback/blocks/tool/edit.rs`) render diffs of *already-applied* mutations; there is no pre-apply gate, no per-hunk Accept/Reject, and no revert. codex's `diff_render.rs` is inline scrollback + a bottom-pane popup modal. Odo's `DiffViewer` with Accept/Reject lanes is already structurally superior — **do not regress** to a presentation-only or modal-only diff model.

3. **Single-occupant / single-foreground-thread session scope** — dsh: "single-occupant today… the staged state can widen to a multi-pane list when concurrent panes land" (`runtime/README.md`); `ui-layout` mounts one conversation column. codex: one ratatui terminal, subagents shown only as history rows + dots (`multi_agents.rs`), agent picker is a list not parallel panes. grok: dashboard is process-local, not cross-host (`23-dashboard.md`). All three fight Odo's "goal/workstream model for concurrent runs." Odo's multi-workstream `Sidebar` + `pendingCounts` is already broader.

4. **Hardcoded unremappable keybindings** — grok: `03-keyboard-shortcuts.md` states bindings "cannot currently be remapped"; terminal-dependent chord sprawl (Ctrl+L vs Ctrl+Enter vs Ctrl+I across VS Code/Apple Terminal/WezTerm) is baked in. A desktop app (Odo, Tauri WebView) should have user-customizable, conflict-free chords — do not inherit a PTY-world assumption. codex's `RuntimeKeymap` with precedence resolution and interactive remap (`keymap_setup/picker.rs`) is the better reference if keymap customization is ever needed.

5. **Read-only background jobs with no completion notification** — dsh `ui-jobs/README.md`: "Rows are read-only — an interrupt written against the current contract would leave the model believing its job is still running." No toast fires on job completion. For unattended runs, observability without control is half the surface. Odo's daemon-driven `notifyRunDone` (App.tsx:268) already does completion notification — keep that.

### What Odo's GUI already does better than all three

1. **DiffViewer with Accept/Reject lanes** — Odo's `DiffViewer.tsx` renders per-file diffs with explicit Accept/Reject lanes backed by daemon `acceptDiff`/`rejectDiff` IPC (`api.ts:203-209`). **None** of the three repos has per-file Accept/Reject lanes: dsh and grok diffs are presentation-only (already-applied); codex's apply-patch approval is a bottom-pane modal popup. Odo's model is a true pre-apply gate, which is the preventive (not forensic) review that the gating ladder requires.

2. **MoA review_diff gating ladder** — Odo's `reviewDiff` IPC (`api.ts:213-215`) blocks daemon-side while "every configured review model grades the diff" (M2 spec), and `autonomyStatus` (`api.ts:219-221`) exposes a gating-ladder rung snapshot. codex's guardian (`on_guardian_assessment`) is the closest analog but is a single-reviewer auto-deny, not a multi-model vote. grok's permission pipeline is per-command, not per-diff. dsh has no review at all. Odo's MoA + gating ladder is the most graduated trust model of the four.

3. **Multi-workstream concurrent-run model** — Odo's `Sidebar` lists workstreams with cross-project status badges (`crossProjectStatus`), `pendingCounts` feeds per-workstream pending-diff counts + running state (App.tsx:178-179), and `createWorkstream`/`deleteWorkstream` manage concurrent runs. dsh is single-occupant. codex has no concurrent-run dashboard in the main TUI. grok's dashboard is process-local (one pager process). Odo's goal/workstream model is the only one designed for concurrent runs from the ground up.

4. **Daemon-driven auto-distill with countdown disclosure** — Odo's `autoDistillCtl` (`api.ts:261-263`) disarms a scheduled auto-distill, and the GUI discloses daemon state (countdown ETA, coverage blocks, in-flight distill list) without owning a trigger (M12: "the GUI discloses daemon state, it never owns a trigger" — App.tsx:239-243). None of the three repos has a comparable daemon-driven, UI-disclosed compaction/distillation scheduler with user-disarm capability. codex's auto-compact is a threshold trigger with no countdown; grok's `/compact` is manual; dsh's compaction is a projection.

## F. Surprises / unexpected finds

1. **grok's leader daemon is the cleanest "agent survives UI crash" decoupling.** The pager is a thin UDS client (`leader_bridge.rs:bridge_leader_connection`); the leader owns the agent and survives a pager crash/restart. `LeaderReconnector` swaps the tx channel and *holds then drops* stale outbound lines rather than replaying them (preventing double-transcript on `session/load`). This is directly relevant to Odo's "long unattended autonomy" — the agent keeps running with no UI attached. Odo's Go daemon already has this property (daemon is separate from Tauri WebView), but grok's reconnect-stale-drop logic is a useful reference for the Tauri↔daemon bridge.

2. **codex's `resume_picker.rs` is 233KB (7010 lines)** — the single largest UI file in any of the three repos. It implements paginated session listing, fuzzy search, cwd/all filter, sort, archive/unarchive/delete, transcript preview loading, resume/fork actions, and dense/comfortable density modes. This is an entire sub-application dedicated to session management — a signal that resume/rewind is a first-class UX problem, not an afterthought.

3. **dsh's slot-based composition is the most extensible UI architecture.** Every UI surface (conversation, tool, plan, jobs, model, sidebar, settings) is a pluggable `cordis.yml` entry that can be retracted by removing one line (`ui-slots/README.md:SlotCore`). Removing `ui-deliverables`'s one entry "removes the guidance, row, and prose links together." This is cleaner than codex's enum-gated `SlashCommand` or grok's `CommandRegistry` — and it's a React pattern Odo could adopt for its component set.

4. **codex has a separate standalone Cloud Tasks ratatui app** (`codex-rs/cloud-tasks/src/ui.rs:draw`) with its own `App` — an independent TUI for browsing/applying Codex Cloud tasks, launched via `codex cloud`. This is the only "second GUI" in any of the three repos, and it shares the same app-server protocol. A template for Odo if it ever needs a separate surface (e.g., a parked-review queue viewer) that talks to the same daemon.

5. **grok's `monitor` tool is a streaming-event-to-notification bridge** — each stdout line from a long-running script becomes a notification in the conversation (`20-background-tasks.md`). This is a genuinely novel interaction primitive: the agent can set up a real-time event stream (log tailing, CI watching, file monitoring) that feeds back into the conversation as notifications, with volume-control auto-stop. None of the other repos has an equivalent. For Odo's "long unattended autonomy," this is a way for the agent to self-monitor without polling.

6. **codex's `git_action_directives.rs` turns assistant prose into actionable UI buttons.** The agent writes `::git-stage` / `::git-commit` / `::git-create-pr` in its markdown response; the TUI parses these into `GitActionDirective` rows rendered as buttons. This closes the loop from "agent describes a git action" to "user clicks a button that executes it" — a pattern that could generalize to any daemon-action (build, test, deploy) in Odo's `MessageBubble`.
