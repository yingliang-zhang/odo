# M0.1 — Polish

## Pain

M0 works but feels rough: the diff viewer is plain text with no highlighting,
the tool ticker shows a bare spinner instead of actual tool activity, the
agent model is hardcoded instead of read from preferences, and I can't attach
a file to give the agent context. (Pain points #3, #4)

## Demo

1. Open Odo. Type: "Read the attached file and add a comment at the top
   explaining what it does."
2. Drag a `.py` file from Finder onto the chat input. The file name appears
   as a chip above the input box.
3. Click Send. The message + file attachment appear in the chat.
4. The tool ticker shows live activity:
   - "Using tool: read → uploaded_file.py"
   - "Using tool: edit → uploaded_file.py"
5. When the agent finishes, the diff card appears with **syntax-highlighted**
   diff text — added lines in green with Python keyword coloring, removed
   lines in red.
6. Click Accept. The file is updated in the project directory.
7. Quit Odo. Reopen. The conversation (including the file attachment reference)
   is restored.

## Scope items

### 1. Diff syntax highlighting

Add lightweight syntax highlighting to the DiffViewer component:
- Parse diff lines: `+` prefix = addition (green), `-` prefix = deletion (red),
  `@@` prefix = hunk header (dimmed), context lines = normal.
- Within added/removed lines, apply basic keyword highlighting for common
  languages (Go, Rust, TypeScript/JavaScript, Python). Use a lightweight
  approach — regex-based token highlighting, not a full parser.
- No external syntax highlighting library. Keep it dependency-free.

### 2. Tool ticker: parse and display actual tool calls

The OMP adapter currently emits only `agent_text` and `agent_done`. For M0.1,
parse the OMP output to extract tool call information:
- OMP print mode text output contains tool usage patterns. Parse these to
  emit `agent_tool_call` and `agent_tool_result` events.
- The ToolTicker component shows each tool call as it arrives (during polling),
  not just a bare spinner.
- Format: "→ tool_name: brief_args" per tool call.
- If parsing fails or produces no tool calls, fall back to the spinner
  (graceful degradation).

### 3. Read model config from ~/.odo/prefs.md

The OMP adapter currently hardcodes `--hermes-provider custom:sudo` and
`--hermes-model t9s/kimi-k3`. Read these from `~/.odo/prefs.md`:
- Parse the `coding:` line to extract `model@provider` format.
- Fall back to hardcoded defaults if prefs.md is missing or unparseable.
- The adapter should resolve this at Start time, not at construction.

### 4. Wire-contract fix: payload.tool vs payload.name

ADR-0002 defines tool call payload as `{"tool": "...", "args": "..."}` but
the frontend renders `payload.name`. Fix the frontend to use `payload.tool`
consistently. Update both MessageBubble and ToolTicker components.

### 5. File attachments (drag-and-drop, clipboard paste)

Allow the user to attach files to a message:
- **Drag-and-drop**: Drop files onto the chat input area. Show file name chips.
- **Clipboard paste**: Paste a file (Cmd+V with a file in clipboard). Show chip.
- On Send: the attachment file path is included in the `user_message` event
  payload as `{"text": "...", "attachments": ["/path/to/file"]}`.
- The OMP adapter includes the attachment paths in the prompt: "Attached
  files: /path/to/file1, /path/to/file2. Read them before proceeding."
- The MessageBubble renders attachment chips for `user_message` events that
  have attachments.
- M0.1 limitation: attachments are file PATHS only (not file contents in
  the journal). The files must exist on disk when the agent runs.

## Architecture decisions for M0.1

| Decision | Value |
|---|---|
| Syntax highlighting | Dependency-free, regex-based, in DiffViewer component |
| Tool call parsing | In OMP adapter, parse print-mode output for tool patterns |
| Model config | Read from ~/.odo/prefs.md at adapter Start time, fallback to defaults |
| File attachments | Paths only in journal, included in prompt text, no file upload/copy |
| Polling | Unchanged — 1.5s interval (M0 decision carries forward) |
