# Composer & IME Handling

- Permanently blue input box root cause: on WKWebView the Enter that confirms an IME candidate can arrive without `isComposing`/`keyCode 229` → submit fires mid-composition → the input session aborts, `compositionend` never arrives, `composingRef` sticks true, and the value-sync guard refuses all future writes; fix clears `ta.value` and `composingRef=false` synchronously after every successful send (Enter/button/⌘Enter converge in `submitDraft`) (UI-epoch-4)
- Composer is uncontrolled for React 19 composition semantics: draft writes from the 350 ms poll / 1 s heartbeat rerender during runs destroyed in-progress Chinese IME composition (ASCII unaffected); programmatic writes (send-clear, slash pick, edit backfill) run via layout effect gated on `!composing`, and `compositionend` syncs committed text back to draft (UI-epoch-2)
- WebKit-only bugs need WebKit harnesses: default Chromium missed both IME bugs, so verification runs a Playwright-WebKit matrix plus a native WKWebView (swiftc) harness; the blue visual itself is untestable outside WKWebView and was pinned at the DOM contract level — stuck-composition submit must leave the box empty, failing pre-fix and passing post-fix (UI-epoch-2) (UI-epoch-4)
- Composer initial-height bug: with the persisted open panel squeezing the textarea to 98 px, WebKit counts the wrapped placeholder in `scrollHeight` (Chromium does not), mis-sizing the mount; fix clears the placeholder during measurement with same-frame restore plus a width-gated ResizeObserver re-size, verified via counterfactual baseline and bundle grep for `.placeholder=""` (UI-epoch-2)
- Known remainder: a 1–2 px height jump on first keystroke (CSS `min-h-[36px]` vs `scrollHeight≈37px` mismatch) was hypothesized but never measured — confirm after the height fix before treating as real (UI-epoch-2)
